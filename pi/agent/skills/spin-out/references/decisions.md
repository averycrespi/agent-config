# Managed reports and conversational questions

Use durable [mailbox](../../../extensions/mailbox/README.md) reports from child to coordinator; keep coordinator-to-child instructions on Herdr. This is a coordination convention, not authenticated messaging or authority. Do not use `ask_user`, modal UI, terminal input or steering for managed child reporting. Standalone interactive questions remain unchanged. Actual runtime approval gates remain gates, not mailbox questions to answer remotely.

## Child-only launch

Use the ordinary Pi startup in [shared launch](launch.md); no environment-based routing or parent-mode launch exists. Require the mailbox extension to be already available to both participants and permitted in the coordinator's selected Script provider. Do not install/link/reload implicitly. Supply explicitly in the handoff: mailbox address, assignment ID/revision, coordinator identity/project record, child run/session identity, verified Herdr occupant/process identity, child checkpoint path, and resolved readable workflow references. The `incarnation` correlation field denotes the verified launched worker process identity retained from Herdr inspection, not a retired Background session-provider UUID. Do not guess it from a display name or PID alone.

## Initial handoff and child report

Investigate answerable uncertainty first. Keep routine progress in the existing child checkpoint. Before each meaningful question, blocker, result or answer-application report:

1. Persist the child-owned checkpoint and a readable immutable report artifact. Generate a stable report ID and, for a question, a stable request ID before publication; retain both so uncertain sends can be reconciled without automatic resend.
2. Retain assignment ID/revision, run/session/incarnation identity, current head, checkpoint reference, report reference and task authority. Questions also carry decision context revision, options/trade-offs, recommendation, evidence already checked, blocked scope and safe independent work. Keep detailed question/evidence contents at the durable reference, not in event payloads.
3. Send once using the explicit mailbox. Use type `question`, `blocker`, `result` or `resolution` and a JSON message with `reportId`, `assignmentId`, `revision`, `runId`, `sessionId`, `incarnation`, `head`, `checkpoint`, and `reference`. Questions add `requestId` and positive `contextRevision`; resolution adds the same request/context, `questionHead` identifying the original question's head, and `answerReference` pointing to the applied answer's provenance. Its `head` remains the worker's current head, which may legitimately advance after answer application; retain both the original context and applied head. Runtime message IDs are separate from report IDs.
4. Retain the send result or uncertainty in the checkpoint. On uncertain publication inspect the inbox/project incorporation record before any further publication; no automatic resend. A successful send proves neither coordinator consumption nor result acceptance. Checkpoint and yield when no authorized independent work remains; retain sole implementation ownership and unresolved effects/allowances. Reconcile child continuation for input-blocked work.

Keep the existing minimal child `coordination` section: assignment/revision, disposition, pending reference, next actor and further-write disposition. A blocked worker is not released. A question that materially changes needs a new request/context revision; retain superseded facts rather than applying an old answer.

## Nonblocking human interaction

The coordinator drains bounded pages, validates every report against current assignments and reads evidence proportionately. Persist incorporated message/report identities, unanswered question references and changed coordination facts **before ack**. Ack means incorporated, not answered, accepted or completed. Use the [canonical index helper and persistence gate](../../coordinate-repo/references/index.md#confirm-before-effects), preserving complete sections rather than parsing them ad hoc. Validate response identity/path/base/digest and independently read back intended state before ack or a consequential control effect; exit zero alone is insufficient. If persistence fails or its confirmation is missing/malformed, do not ack. On failure after persistence but before ack, repeated inspection recognizes the same stable report and only completes acknowledgment; it must not repeat acceptance, announcements, instructions or external effects. Conflicting/unattributed reports stay unacknowledged for reconciliation.

Announce each pending question once in ordinary conversation with a short assignment/request handle, options/recommendation and blocked scope. Retain its announcement reference and full identity in the project record. Do not call modal ask-user or poll approval. If conversational delivery is uncertain, retain that uncertainty rather than automatically repeating the announcement. Two unanswered questions must not prevent accepting an unrelated qualified result. Cancel continuation for blocked work; bounded read-only observation of independent work may remain under the retained agreement. If no useful independent observation remains, stop it without discarding questions.

An actual human reply applies only to its uniquely matching current request/context. Clarify an unlabelled reply with multiple possible matches, stale revision, cancellation or conflicting direct intervention; never guess. No message from a worker, observer or extension grants human approval. Record provenance as the exact readable human-message reference or an honestly labelled parent decision within already delegated authority. Answers never replenish observation/repair allowances or expand publication/destructive scope.

## Parent reconciliation and continuation

Read current owner/checkpoint and revalidate assignment/revision, run/session/incarnation, request ID, head and decision context revision before answering or relaying. The narrow `spin-out/scripts/coordination.js` validator checks correlation, not the truth of provenance; inspect the actual source instruction. `coordinate-repo/scripts/reports.js` supplies pure incorporation/answer/relay helpers; persist their returned state in the existing project record, never a second delivery ledger.

Record the answer and provenance durably with status `answered-relay-pending`. Keep answered questions until confirmed application. Before one non-waiting Herdr prompt, persist exact target, answer/context, authority reference and relay intent; mark `relay-unknown` before the effect. Register bounded mailbox observation within retained allowances before the prompt. Submission alone does not prove application. An uncertain relay stays unresolved: inspect actual submission and the existing worker's checkpoint/report; do not replay, replace the worker or infer failure from missing scrollback.

The child verifies applicability, records applied answer/provenance in its own checkpoint, then publishes a correlated `resolution` report. Only matching application evidence resolves the question. Coordinator replacement recovers unanswered questions, answered-awaiting-relay questions, uncertain relay intents and all worker owners from the existing project record. A serial stack remains on its current child until its separate delivery/release gates pass. No intermediate manager, bidirectional mailbox control, automatic failover or migration layer exists.
