# Ticket State Helper

Read this interface completely before invoking the helper. Follow [work-ticket](../SKILL.md); load [recovery](recovery.md), [publication](publication.md), or [settlement](settlement.md) before the corresponding operation. Paths to `scripts/ticket-state.js` are relative to the skill root, one directory above this reference.

Run `node <absolute-skill-path>/scripts/ticket-state.js` with one JSON request on stdin; never interpolate ticket prose into shell arguments. Responses are `{result: ...}` or `{error: ...}` with nonzero exit on failure. No user configuration or separate retained logs; state remains locally until explicitly authorized cleanup. State files are owner-only and bounded to 256 KiB. Locks/CAS/atomic rename protect cooperative users, not hostile processes or all power-loss cases.

All requests include absolute `cwd` and immutable `ticketId`. `status` reads the record; `snapshot` observes Git without updating evidence. Every mutation after initialization includes `runId`, `owner`, `expectedRevision`, and the stored `contract` baseline. Reread after writes. Never fabricate authorization, owner-release, check, or external-confirmation evidence: the helper validates consistency, not the truth of agent-supplied observations, and cannot intercept arbitrary shell/broker writes.

No phase cursor.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `reconcile`         | `observations` covering fresh ticket/files/Git/PR/check/owner state; `previousOwnerReleased: true` only for a proven owner takeover. | `authorize`         | Explicit new `authorization` evidence and authorized `contract`; invalidates old scope evidence without resetting repair count. For an explicitly requested local follow-up, submit this complete shape with freshly read values (not stale revision numbers); use `contract` for the **stored** baseline and `newContract` for the newly authorized outcome/AC/scope, even when unchanged:

```json
{
  "action": "reopen_local",
  "cwd": "/absolute/repository/root",
  "ticketId": "11111111-2222-3333-4444-555555555555",
  "runId": "stored-run-id",
  "owner": "stored-owner-id",
  "expectedRevision": 15,
  "contract": "Exact stored baseline",
  "newContract": "Authorized baseline including the requested follow-up and acceptance criteria",
  "authorization": {
    "operations": ["implement", "commit"],
    "boundary": "local",
    "evidence": "Actual user request explicitly authorizing follow-up changes and a local commit after handoff"
  },
  "plan": [
    {
      "step": "Implement the requested follow-up",
      "verification": "Focused regression tests and required repository checks",
      "status": "todo"
    }
  ],
  "fingerprint": "sha256:<64 hex digits from a fresh snapshot>",
  "observations": "Fresh ticket/files/Git/PR/checks/ownership observations; same sole writer, no PR or unresolved effects",
  "planeState": "In Progress",
  "noPrConfirmed": true
}
```

Reread `status` after success. The operation increments revision once and records the prior revision, owner, scope/authority, plan, handoff progress, snapshot, evidence, review, finding dispositions, repair count, and reconciliation in append-only `localFollowups`. Existing schema-version-1 records need no migration. Historical evidence is not current evidence; current review remains stale until independently refreshed. Archives share the 256 KiB state limit; overflow rejects atomically rather than dropping history. Do not prune/reset history to make reopening succeed.

PR settlement gates and pending writes require `mergeConfirmed: true` and exact `mergedHead`. Cleanup gates and pending writes require `noLiveWriter`, `noUnpushedWork`, and `prDispositionKnown` all true plus matching `planeState: Done/Canceled`. Establish the fresh observations and prerequisites in the settlement procedure before supplying these fields; do not infer them from authority alone.
