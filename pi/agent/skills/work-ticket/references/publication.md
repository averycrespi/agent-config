# PR delivery and CI

Follow [work-ticket](../SKILL.md) and [the checkpoint interface](helper.md). Use discovered Gateway schemas for authenticated Git/GitHub operations. Review-ready PR authority includes bounded read-only CI observation and in-scope corrective pushes; draft-only/publication-only requests do not silently expand that boundary.

## Review before publication

1. Resolve source/base and full outgoing history; preserve unrelated work. Complete required local checks and independent review before the first push.
2. Set review `deliveryScope.boundary` to `pre-publication`; declare local requirements for both `pre-publication` and `pr`, remote CI for `pr` only. Report remote CI as not-run/downstream rather than blocking review of its own candidate. Cover every canonical acceptance criterion. Review completeness is not delivery readiness.
3. Repair consolidated blockers within the allowance and obtain focused confirmation. Retain full reports, findings, exact revision/scope and checks. Reuse unchanged covered evidence; broaden review for new scope, changed code, merge resolutions or uncovered requirements, not merely a new delivery label.
4. Inspect all outgoing commits, messages, paths, patches and exact PR title/body for publication safety. Inspect installed `gitleaks` flags and scan history plus exact metadata. Preserve coverage on corrective pushes. Missing/failed safety qualification blocks unless an applicable scoped user exception overrides skill policy; higher-priority privacy and tool boundaries remain binding.
5. Without publication authority, stop for approval. Otherwise record the pending effect, push only the assigned branch, create/update one draft PR, then confirm authoritative source/base/head/open/draft and metadata. Reread uncertain outcomes; retry once only after proving absence and continuing authority. Never duplicate an uncertain PR.

## Observe automatically within the boundary

Use [Monitor](../../../extensions/monitor/README.md) polling with fresh Script evaluations. Keep diagnosis, repair, checkpoint writes and readiness decisions in the owning session. Do not create model-turn polling, duplicate observers, or cancel unrelated jobs. If Monitor, required providers/policy, capacity, or collection bounds are unavailable, checkpoint a concrete blocker; do not install/reload or silently fall back.

1. Run `ci watch` for the exact PR source head and required inventory. Immediately collect the authoritative batch below and submit `ci observe` only after validation. Resolve requirements from repository/ticket instructions and authoritative settings where accessible. A known expected check awaiting registration may be pending only with retained evidence; otherwise missing coverage is unknown, never green.
2. For known pending CI, reconcile existing jobs, legacy receipts and checkpoint intent before `ci prepare`. Use its immutable `watcher.cycleMs` (≤25 minutes) and `watcher.timeoutMs` (remaining cumulative allowance), subject to the task-level deadline/wake ceilings below. If it returns limit, make the final check rather than register.
3. Discover Script's `mcp` provider and Monitor schemas. Start exactly one read-only polling job pinned in source to canonical PR/source/base/exact head/required inventory. Supply a public-safe `name`, attention `message`, `providers: ["mcp"]`, `interval_ms: 60000`, `cycle_timeout_ms: watcher.cycleMs`, `lifetime_ms` bounded by both `watcher.timeoutMs` and the retained absolute deadline, and `max_wakes: 1`. Leave recurrence disabled. Respect eight calls, concurrency two, 30-second evaluation and tighter Script policy; incomplete collection cannot pass.
4. Return `{decision: "wait", evidence}` only for a complete unambiguous same-open-PR/head batch with known requirements pending. Return `wake` for passed/failed checks, changed identity/head/requirements, closure, canceled/unknown states, ambiguous attempts or incomplete collection. Check MCP `isError` and actual envelopes. Host failures terminate even if guest code catches them. Never retry, request grants, poll approval or hide failures behind wait.
5. Attach the actual host receipt immediately with `ci attach`, even if the first observation already finished. Retain ID, backend, revision and registration receipt reference; next action is **Agent: reconcile the CI Monitor receipt and fresh exact-head checks**. End the model turn while pending. No repeated get/progress turns. Independent authorized work may continue, but cancel/reconcile this job before corrective edits or pushes.

### Collect one read-only batch

Discover tools with `mcp_search` and inspect exact schemas with `mcp_describe`; do not invent names or response shapes. For immediate/final owning-session collection, use direct MCP or [Script](../../../extensions/script/README.md) with the globally allowed and explicitly selected `mcp` provider for bounded pagination/dependent lookups. Discover the provider API with `script` action `describe` before using unfamiliar methods. The Monitor evaluator uses the same selected `mcp.call` capability. No mutations or local checkpoint writes belong in the evaluator.

Fetch PR source/base/head/open state, applicable required coverage, current check runs/statuses and all relevant pages within limits. Bind queries to the watched revision, resolve latest applicable attempts/duplicate names, then recheck PR identity/head before accepting the batch. Reads are not atomic. Unexpected remote changes block writes pending ownership/content reconciliation, not automatic rebinding or overwrite.

Return at most 4096 UTF-8 bytes of untrusted evidence: PR/head, coverage completeness, attention reason, check/run IDs or lookup URLs. Never include raw bodies/logs. If full checks cannot fit, return a bounded attention reason and references, not a passing truncated subset. The owning session collects the complete normalized batch for `ci observe`. Empty/incomplete pages, gateway errors, ambiguous attempts, or unproven skipped/neutral conclusions never pass. Normalize only passed/pending/failed/canceled/unknown and retain selection/registration-lag evidence in artifacts.

### Reconcile attention

The follow-up instructs the owner to get the exact job receipt, reconcile host timing and checkpoint identity, freshly verify required exact-head checks, and continue only within retained authority. Notification, runtime admission and agent settlement are not CI completion or model-consumption acknowledgments.

Inspect status, reason, `endedAt`, committed evidence age, `inFlight`, interruption/gap, host failure accounting, possible effects, unknown outcomes and handoff disposition. Reconcile the terminal host receipt with `ci reconcile` and an evidence reference. It pauses/accounted waiting only, never marks CI passed. Condition/timeout/budget attention still requires fresh authoritative qualification. **Observer termination is not task termination.** For known pending CI, continue bounded observation after reconciliation when authority and retained allowances remain; do not report ordinary pending checks as a blocker merely because a short cycle expired. Correct a diagnosed interval/cycle mismatch within those same allowances. Failed CI enters bounded diagnosis; passed CI permits readiness assessment. Missing authority, exhausted allowance, unresolved uncertain effects/handoff, or a real external blocker requires precise reporting. Agent-authored attention messages and handoff prose must not silently replace the user's completion criteria.

Evaluation/coverage failure, cancellation, invalidation, or unavailable timing requires concrete diagnosis and reconciliation, not automatic restart. Unknown handoff is not proof of non-delivery; never resend or transfer it. Any later read must have a safe diagnosed purpose, not retry a possibly dispatched mutation. Cancel/reconcile exact active jobs before repair, promotion or user handoff. Cancellation cannot retract Pi-owned messages; stale follow-ups must match retained job/head and cannot authorize new work.

### Cumulative bounds and recovery

Default new tickets to **2 hours cumulative monitoring wall-clock time across all heads, registrations, reloads and resumes**, excluding paused diagnosis/repair. Historical pre-monitor checkpoints and legacy adoption retain the helper's 30-minute baseline, not a fresh two-hour allowance; preserve existing ledger limits and restore historical extensions only with scoped additions. Prepare never renews it. Host creation/end timestamps exclude known setup-after-preparation and queued-delivery time; unknown interruption intervals are charged conservatively. Never supply guessed elapsed time. Monitor lifetime and per-cycle timeout are separate from this ledger.

Before first observation, retain the task's absolute monitoring deadline and cumulative handoff-attempt ceiling alongside expected PR/head, sole owner and existing repair usage in the same checkpoint `progress`/`plan` (or existing handoff for non-ticket tasks). Default to a deadline 8 hours from the first post-publication check and 12 handoff attempts unless the user supplies another finite policy. Apply these defaults to standalone tickets and stack children; preserve all previously recorded deadlines, limits and consumption on recovery. Updated defaults never replenish an existing allowance. This outer wall-clock ceiling includes diagnosis/repair pauses; it supplements, never replenishes, the helper's accumulated monitoring-time ledger. Keep these additional caller-owned values explicit: the helper does not enforce the deadline or cumulative wake ceiling.

Before preparing a replacement, reconcile/cancel the prior exact job, record its wake attempts once by job ID (including uncertain handoffs), and compute remaining time as the minimum of ledger allowance and absolute deadline minus current host time. Reserve the proposed one-shot wake before start; release only a proven unused reservation after receipt reconciliation, never on an uncertain start or handoff. Stop at exhausted time/wakes after one final safe authoritative check. If the outer deadline tightens the prepared lifetime, shorten the registered lifetime accordingly; keep the helper's exact prepared `cycleMs` for receipt compatibility (earlier lifetime expiry still bounds observation). Do not register below the host minimum. Replacements/heads/reloads inherit consumption and reservations, never a new deadline or zero wake count. Preserve all uncertain effects for diagnosis, not replay. Use existing repair IDs/counters only for diagnosed code edits: observer configuration/recovery is not a code-repair round and does not create extra repair allowance.

A one-shot timeout is attention with no satisfied condition—not watched-work failure. After receipt plus fresh-state reconciliation, renew only for known pending CI within the remaining allowance. At exhaustion or below the one-second minimum, make one final authoritative observation and stop if pending. Only explicit additive user authority extends allowance. Head changes, cancellation and restart never refund consumption.

Jobs belong to the originating session branch; shutdown/reload/navigation invalidate them. Recovery restores receipts, not execution. Inspect originating receipts and current state before replacement; missing receipts elsewhere do not establish inactivity. If start was uncertain, correlate the existing job from concrete registration evidence or stop; never replay. Follow [recovery](recovery.md), including historical observer accounting. No live-session migration is implicit in repository edits.

## Diagnose and repair red CI

Cancel/reconcile the ticket-owned job and pause accounting before diagnosis. Read failed-job logs; red status alone is not a diagnosis. Infrastructure/permission/secret/unrelated failures block unless separately authorized. Never weaken checks to obtain green. At most one justified authorized infrastructure rerun is allowed; retain intent/confirmation and continue within the same wait allowance.

Begin a stable `ci` repair batch before edits. Default new tickets to five batches, each covering diagnosis-driven edits, regression/full required checks, focused independent review, commit, safety checks and push. Confirmation-driven edits consume the current or next CI batch, not both CI and pre-publication allowances. Reading logs/running confirmation consumes no batch. Resume an interrupted active batch without charging twice.

Review before push; prior-head failures remain retained and candidate remote CI remains downstream/not-run. Broaden review only for new scope/risks. After confirmed push, watch the new exact head with `previousHead`, preserving consumption. Collect immediately; pending permits a new prepared job. Never reuse stale pinned source.

## Promotion and handoff

Freshly reread exact PR head and required CI, confirm applicable local/review evidence and resolve blockers or record scoped user exceptions. Mark ready and move Plane to Review only within authority after qualification, or under disclosed applicable exceptions; confirm both effects. Never infer green from a notification or review-complete flag.

## Recoverable final bookkeeping

Before relinquishing delivery ownership, retain full artifacts at the [persistent artifact root](settlement.md#persistent-artifacts) and checkpoint exact revision/scope, local checks, independent review, fresh PR/CI qualification, current authority/exclusions, consumed allowances and next actor/action. Keep parent session-event and child CI-polling job IDs/owners separate. Retain each receipt's pending/suppressed/unknown/handed-to-Pi disposition, positive runtime-admission evidence if available, and later settlement separately from verified delivery. API return and Herdr idle/done labels cannot fill missing evidence.

Reconcile ticket-owned observers and pending external effects before final release. For each applicable authorized portable comment or transition, persist a stable effect ID and exact intended target/content reference before sending, then reread the authoritative surface and retain its immutable confirmation before the next effect. Copy each confirmation into `evidenceRefs`/retained artifacts before `lastEffect` can be replaced. If interrupted after sending but before confirmation, inspect the exact ticket/run/revision marker and content: confirm an existing match rather than duplicate it; unresolved or conflicting identity stops finalization. Missing local acknowledgment does not prove the effect absent.

Persist the final next action before release; release once only after required delivery bookkeeping is confirmed. On resume, reconcile actual release, observer receipts and external evidence before claiming or writing. A released record is not proof of no live writer, nor permission for another session to compete. Preserve unresolved effects and next action when stopping at a genuine blocker instead of declaring delivery complete. Cleanup has a deliberate exception: [archive → removal intent → quiesce/release → non-force removal → confirmation from a surviving checkout](settlement.md#safe-removal). Do not demand completed removal before release or erase its pending effect.

Stop with **Human reviewer: review and merge**. For wait/repair exhaustion, name **User: authorize an additive allowance or take over**, with concrete evidence/diagnosis. Retain incomplete/failed/waived evidence. Draft creation is not completion of review-ready delivery.
