# PR Delivery and CI

Follow [work-ticket](../SKILL.md) and [the checkpoint interface](helper.md). Use discovered gateway schemas for authenticated Git/GitHub operations. Respect the explicit delivery boundary: review-ready PR delivery includes bounded monitoring and corrective pushes; draft-only or publication-only instructions do not silently expand that authority.

## Review before publication

1. Resolve correct source/base and full outgoing history. Preserve unrelated commits. Complete applicable required local checks and independent review of the intended PR scope before the first push.
2. Use the review workflow's existing evidence boundaries: set `deliveryScope.boundary` to `pre-publication`, declare each local requirement for `pre-publication` and `pr`, and declare remote CI for `pr` only. Supply remote CI honestly as `not-run`, with a downstream-qualification explanation. Cover the full canonical acceptance criteria; do not omit requirements to manufacture a complete review. A review complete at this boundary is not delivery readiness.
3. Repair consolidated blockers within the review allowance and obtain focused confirmation. Preserve full reports, covered revision/scope, findings, and check references. Reuse review when its content and requirements remain covered; publishing an unchanged reviewed commit does not require duplicate review. A new boundary label alone is not a code change. Reevaluate coverage for expanded scope, changed code, merge resolutions, or newly required qualification.
4. Inspect complete outgoing commit history, messages, paths, patches, and proposed PR metadata for publication safety. Run installed `gitleaks` against history and exact title/body, inspect supported flags, and honor repository public-content rules. Preserve history/metadata scan coverage for corrective pushes too; reuse unchanged coverage only with concrete evidence. Missing/failed safety qualification blocks by default. A scoped user exception can change only an overridable skill policy, never higher-priority secret/data rules or tool approvals.
5. If publication lacks authority, stop with **User: approve pushing and opening the PR**. Otherwise record the exact pending effect, push only the assigned branch, and create/update one draft PR. Confirm authoritative head/source/base/open/draft and public-safe metadata; retain tracking and PR identity. Reread ambiguous outcomes before retrying; retry once only after proving the effect absent and still authorized.

## Monitor automatically within the boundary

Use the session-bound [Monitor extension](../../../extensions/monitor/README.md) for waiting and the owning agent for diagnosis, repair, and readiness decisions. An authorized review-ready PR request includes this bounded read-only monitoring; draft-only or publication-only requests do not. Do not start a Loop for CI, commandeer an unrelated Loop, or cancel unrelated monitors. If Monitor is unavailable, disabled, at capacity, or unable to collect the required batch within its limits, checkpoint the blocker and next actor/action rather than silently fall back to model-turn polling.

1. After publishing, run `ci watch` for the exact PR source head and required-check inventory, then collect an immediate authoritative batch as described below. Resolve requirements from repository/ticket instructions and authoritative settings where accessible. Empty results are not success. Submit `ci observe` only after validating the full batch. A known expected check awaiting registration may normalize to `pending` only with retained evidence that it is expected; missing coverage without that evidence is `unknown`/blocked, never passed.
2. If legitimately pending, inspect existing Monitor receipts and the checkpoint to avoid duplicate registration. Run `ci prepare` in the owning session. Its compact receipt records registration intent and supplies a bounded `watcher.timeoutMs`; if it returns `limit` without a watcher, perform the final qualification described below instead of registering.
3. Register exactly one read-only `monitor start` pinned in its source to the canonical PR, source/base identity, exact source head, and required inventory. Use a public-safe name identifying the ticket/PR/head, `interval_ms: 60000`, and `timeout_ms` from the prepared intent. Respect Monitor's per-poll time/call/concurrency limits. Its first poll runs promptly, then subsequent polls run no sooner than 60 seconds after settlement. Bind the returned host receipt with `ci attach` immediately. Never substitute a model-calculated lifetime or elapsed time.
4. In the observer, return `wait` only after a complete, unambiguous observation shows the same open PR/head and known required coverage still pending. Return `notify` for all required checks passing, a failed required check, closure/identity/head/requirements changes, unknown/canceled states, ambiguous attempts, or incomplete collection. These are attention signals, not promotion or repair authorization. Let Monitor terminate on executor/gateway failures according to its failure rules; do not add retries or hide host failures behind `wait`.
5. After registration, checkpoint the Monitor ID, watched revision, registration receipt reference, and **Agent: reconcile the CI monitor notification** as the next action. End the model turn; do not repeatedly call `monitor get` or generate progress turns while waiting. Independent already-authorized work may continue, but stop/reconcile this watcher before editing or pushing a corrective head.

### Collect one read-only batch

Discover gateway tools with `mcp_search` and read exact schemas with `mcp_describe` before composing the observer; do not invent GitHub tool names or response shapes. Use the same collection rules for the owning session's immediate/final check, with [code mode](../../../extensions/code-mode/README.md) for pagination and dependent lookups or direct MCP tools for a simple call. Keep all mutations outside the observer: no reruns, pushes, promotion, Plane updates, or local checkpoint writes.

Fetch PR identity/source/base/head/open state, applicable required-check coverage, and current checks/statuses. Bind check queries to the watched revision where supported, consume all relevant pages within the active call/time limits, and resolve latest applicable attempts before normalization. Recheck PR identity/head before accepting the batch; these reads are not an atomic snapshot. Unexpected remote changes stop automatic writes: reconcile ownership and content rather than rebinding the watch or overwriting another actor.

Return bounded untrusted evidence with PR/head identity, collection/coverage completeness, disposition reason, and check/run IDs or URLs sufficient for fresh lookup. Keep Monitor evidence within its 4096-character limit; do not embed logs or raw response bodies. If full normalized checks do not fit, return a bounded attention reason and lookup references, not a success-looking truncated subset. The owning session collects the full normalized batch before submitting `ci observe`. Never infer a passing requirement from an empty result, incomplete pagination, gateway error, ambiguous attempt, or unproven skipped/neutral conclusion. Normalize only supported `passed/pending/failed/canceled/unknown` states; retain selection and registration-lag evidence in referenced artifacts, not extra helper fields.

### Reconcile notifications in the owning session

The Monitor follow-up should instruct: inspect the registered Monitor receipt and checkpoint; reconcile host timing; freshly verify the pinned PR/head and required checks; then continue only within existing delivery/repair authority. Notifications may queue behind active work and are not proof of current CI. Read `monitor get` by checkpoint ID and verify that any evidence belongs to the relevant observation, especially after executor failure.

Use `ci reconcile` with the exact terminal host receipt and its reference. It charges monitoring through `endedAt`, pauses timing, and permits immediate fresh observation even before the previous 60-second due time. It does not mark CI passed. For a normal condition/deadline notification, collect fresh authoritative evidence, validate the complete batch, and submit `ci observe`: `waiting` permits a new bounded registration; `repair` starts diagnosis only within authority/allowance; `blocked` or `limit` stops; `passed` permits final readiness assessment. Closure, identity changes, and unresolvable coverage remain blockers regardless of individual green checks.

For executor/gateway failures or incomplete collection, inspect safe failure and partial/unknown-effect metadata first. Checkpoint the blocker rather than automatically rerun the observer or replay failed calls through code mode/direct MCP. Any subsequent read needs a diagnosed, safe, still-authorized purpose; a notification is not blanket retry permission. Before repair, deliberate user handoff, or promotion, cancel any still-active watcher by its recorded ID and reconcile its terminal receipt. Canceling cannot retract a follow-up already handed to Pi; stale follow-ups must be matched to the retained watcher/head and cannot authorize new work.

### Bound waiting and recovery

Default allowance is **30 minutes of cumulative monitoring wall-clock time across all heads and resumes, including background polling but excluding paused diagnosis and repair**. `ci prepare` preserves consumed time and reserves a finite registration lifetime. `ci attach` binds host creation/deadline timestamps; registration setup after prepare is excluded when that receipt is known. Before attachment, an interrupted open intent is conservatively charged from preparation. `ci reconcile` computes consumption from host timestamps, excluding time a terminal notification spent queued. The model never supplies elapsed estimates. Per-registration/configured limits remain additional ceilings, not a fresh ticket allowance.

At exhaustion (or less than Monitor's one-second minimum lifetime), permit one final authoritative observation; stop if still pending and do not register again. Only an explicit additive user allowance can resume waiting. A terminal receipt by itself never satisfies required checks. Cancellation/reload/head changes do not replenish budgets.

Monitor runs only in its originating active session branch. Reload, shutdown, and navigation invalidate it without automatic restart. On recovery, read the checkpoint and originating receipts before registration; reconcile exact terminal timestamps, or conservatively charge the open interval through recovery when the terminal time is unavailable. Prove an unknown registration absent/inactive before `ci recover`; a missing receipt in the current branch is not proof. Never replay an uncertain registration. See [recovery](recovery.md) for reconciliation and migration from older Loop-driven checkpoints.

## Diagnose and repair red CI

Cancel any active ticket-owned Monitor and reconcile its host receipt before repair; keep CI accounting paused during diagnosis and corrective work. Read failed-job logs and diagnose before editing; a red status alone is not an actionable bug. Treat infrastructure/permissions/secrets and unrelated failures as blockers unless explicitly authorized to address them. Do not weaken checks or acceptance criteria to obtain green. At most one justified, authorized infrastructure rerun is allowed; record its pending effect and confirmation, then continue observing within the same wait allowance. Preserve the rerun reference across recovery.

For an in-scope failure with corrective-push authority, begin a stable `ci` repair batch before editing. Default allowance is **two batches**. Each batch includes diagnosis-driven edits, regression and required checks, focused independent review, commit, safety checks, and corrective push. If confirmation requires another edit batch, finish the current batch and consume the next CI batch—not both CI and pre-publication review allowances. Merely observing or confirming consumes no repair batch. Resume the active batch after interruption without charging twice.

Review the repair before pushing. Prior-head CI failures remain in diagnostic history; candidate-head remote CI is honestly downstream/not-run, not falsely passed or a prerequisite for reviewing its own fix. Broaden review only for new scope or affected risks. After confirmed push, `ci watch` the new head with `previousHead`; retain waiting and repair consumption. Collect the immediate new-head batch; if pending, prepare and attach a new Monitor within the retained remaining allowance. Never reuse the old observer's pinned head or reset consumption.

## Promotion and handoff

Before promotion, reread exact PR head and required CI, verify applicable review/local evidence still covers the delivered change, and resolve blockers or record specific user-accepted exceptions. Do not infer readiness from `complete` alone or from stale CI. Mark ready and move Plane to Review only within authority and after normal qualification passes, or under clearly recorded applicable exceptions. Confirm both effects.

Stop with **Human reviewer: review and merge**. For waiting exhaustion name **User: authorize additional monitoring allowance or take over**; for repair exhaustion name **User: assess the diagnosis and authorize additional repair or take over**. Keep incomplete/failed/waived evidence visible. PR creation alone is not completion of a review-ready delivery request.
