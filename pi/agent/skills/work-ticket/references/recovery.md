# Ticket Recovery

Read this procedure completely before resuming after compaction/interruption, taking over ownership, or recovering a helper failure. Follow [work-ticket](../SKILL.md) and read [the helper interface](helper.md) before helper calls.

Read the existing record first, then reconcile actual ticket, files, Git, ownership, PR, review, and checks before acting. A record is not proof of process liveness or external effects. Preserve the plan, unfinished repair batch, finding dispositions, and repair count. Reuse evidence only for the relevant unchanged revision and scope; code changes invalidate affected evidence. The helper conservatively invalidates whole-snapshot evidence on any HEAD/diff/untracked-file change; reuse narrower evidence only after independently establishing that its coverage is unchanged and recording that justification.

For post-removal cleanup recovery, use the external cleanup journal procedure below instead of trying to bind a helper call to a nonexistent checkout.

Resume the same run rather than initialize another attempt. Prove a previous owner absent/released before taking over; a helper lock does not enforce editor/process isolation. Cross-check portable claims and actual workers before starting. Stop on duplicates, malformed state, branch/base drift, or unresolved ownership. After a helper crash, inspect `.pi/tickets/.writer.lock/owner.json` and prove its process absent before separately removing that exact stale lock; never delete ticket state to get unstuck.

## Publication after local completion

For an explicit push/PR request on an unchanged `local_complete` delivery, read [publication](publication.md) and use `begin_pr` with the same run/owner, fresh CAS/snapshot and publication evidence. Do not invent a coding request or use `reopen_local`; ordinary `authorize` and `reconcile` remain unable to resume terminal delivery. `begin_pr` archives prior completion, retains current checks/review for unchanged scope, clears safety/CI, and preserves all repair consumption. It cannot reopen `awaiting_human`, Done, or Canceled, combine owner takeover, bypass unresolved effects, or authorize settlement/cleanup. After a successful transition, recover pending publication writes through ordinary reconciliation; do not repeat `begin_pr` or any confirmed write.

## Explicit follow-up after local completion

Keep completion sticky for ordinary resume, reconciliation, authorization updates, and unsolicited review suggestions. Only an explicit user request for additional implementation after local handoff permits `reopen_local`; do not use `init`, delete state, or switch to untracked ordinary coding to bypass the completed attempt. `authorize` alone still cannot reopen it.

Before reopening, reread `status` and inspect the actual ticket, files, Git branch/base, current checks, PR absence, and sole-writer ownership. Require Plane In Progress, `local_complete`, local prior boundary, no recorded or actual PR, and confirmed implementation-only external history. Stop on unresolved effects or ownership conflicts. This operation requires the existing owner; it cannot combine reopening with takeover. PR delivery (`awaiting_human`), Done, and Canceled retain their existing lifecycle safeguards and cannot use this path.

Record the actual follow-up request, explicit scope/AC baseline, local authority (`implement`, plus `commit` unless excluded), and follow-up plan in one `reopen_local` request using the helper interface. Supply the stored contract and CAS revision plus a freshly observed snapshot fingerprint. This is fresh authorization, not inherited permission: publication, settlement, cancellation, and cleanup are not carried forward or granted. Do not supply invented observations; helper consistency checks cannot establish remote truth or user consent.

Reread the result before editing. Continue the same run and owner with the retained findings/dispositions, external-write keys, and consumed repair allowance. Prior delivery is archived in `localFollowups`; all current verification/safety/CI evidence is cleared and existing review becomes stale even if scope and files are unchanged. Record new checks and refresh any existing review before the next handoff; remaining automatic repair cycles are shared across all follow-ups. Reopening never refunds exhausted repairs. Preserve unrelated edits and stop on material drift; a matching snapshot is not permission to include unrelated work. After successful reopening, ordinary interrupted-run recovery applies again.

Reconcile pending external writes by rereading the authoritative surface first. Retry once only after proving the effect absent and confirming it remains authorized and safe. Do not repeat confirmed writes or reset consumed repair cycles. Inspection-only requests do not authorize state writes or takeover.

## Accepted merged deliveries and interrupted cleanup

Read [settlement](settlement.md) before these operations. When an incomplete review or superseding shared-PR head prevents ordinary settlement, preserve that evidence and use `accept_merged` only under the actual applicable user instruction accepting the exceptions. Reread `humanAcceptance` after interruption; do not repeat acceptance, rewrite publication history, restore cleared evidence as passing, or invent a handoff transition. Resume the same run and use the recorded merged PR/head when confirming settlement. Process every ticket sharing a checkout independently before cleanup; no historical review success is needed to clean up confirmed human-accepted deliveries.

Before removal, retain the durable `archiveDir` and `cleanupId` outside the source checkout and in the owning session's handoff. After an interruption:

1. Read `cleanup_status` using only the external directory and ID. Verify every retained ticket/run/owner, source checkout/workspace intent, journal revision, evidence digests and outcome. Do not infer actual removal from `pending`.
2. Reread authoritative Herdr/worktree inventory, exact source-path existence, writer liveness, Git/remote retention, and affected PR/Plane dispositions. Never focus or interrupt unrelated workers to perform cleanup.
3. If the exact checkout is already gone, call `cleanup_confirm` with the fresh journal revision, identity list, key/intent and inventory evidence. It does not require the original Git checkout or branch. If already confirmed, report the recorded effect; never repeat it.
4. If the checkout remains and reread proves the effect absent, call `cleanup_retry` with fresh complete safety observations and every retained ticket CAS. The helper rechecks unchanged source state/evidence and consumes its one retry before another external call. Then remove without force, reread and confirm. Changed state/evidence, unresolved partial effects, new writers, unsafe work, or exhausted retry require a blocked handoff with the retained journal, not deletion/reset or an invented success.

For an old removed checkout with byte-preserved `state.json`/handoff and a checkout-local pending cleanup intent, do not edit the original archive or append another unsupported receipt. Use `adopt_cleanup` in a new durable directory with the exact original state digest, immutable ticket/run/owner/revision/contract, matching pending key/intent, actual cleanup authority, confirmed Plane/PR disposition, and archive provenance/removal observations. Reread the resulting journal and use `cleanup_confirm`. The old pending state and any old receipt stay unchanged as historical evidence; the supported journal records the authoritative cleanup outcome. Adoption is recovery-only and cannot authorize removal of a new or recreated checkout.

If original state/evidence is missing, identities conflict, or the source path has been recreated, stop rather than reconstructing a success. Journal and checkout locks follow the same cooperative stale-lock rule: inspect the exact `.writer.lock/owner.json`, prove its process absent, then remove only that stale lock. Keep all archives until deletion is separately authorized. Locks, filesystem checks and CAS do not enforce honesty of process/remote/user attestations or protect against hostile concurrent filesystem writers.
