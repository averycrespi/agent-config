# Work-stack verification

Use three distinct evidence layers: discovery/link checks, read-only model scenarios, and a controlled live two-child exercise when authorized. None substitutes for unperformed real ticket/PR/CI delivery. Retain the exact skill revision, prompts, full responses, parent decisions, and gaps outside tracked source; publish only a sanitized summary.

## Deterministic checks

Run the repository's skill discovery/link tests and formatting checks. The work-ticket skill test follows local Markdown links recursively; include work-stack in that inventory. These checks validate packaging, not obedience, stack completion, or external qualification. There is no new stack helper/state machine to unit-test. Run applicable full checks if code or runtime configuration changes.

## Read-only decision scenarios

Give each independent scenario agent the actual skill and related contracts plus a self-contained fixture. Treat the observations below as synthetic input, not live external facts. Request its next action, evidence needed, authority limits, and stopping decision; compare its full response against the expected outcomes. Do not prompt it with the expected answer. Use generic ticket identities resolved to distinct fixture UUIDs, and full fixture SHAs rather than ambiguous branch labels.

| Scenario                                   | Supplied observations                                                                                                                                                                  | Expected outcome                                                                                                                                                                       |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Two serial local successes                 | Ordered A then B; base H0; A's committed H1 has required local/review evidence, clean tree, released owner, no effects/watchers; B then delivers H2 with the same qualification        | Reconcile A before launching B at H1, targeting A's branch; review H1..H2 while testing H2's cumulative tree; no push; final report records both heads and predecessor-first order     |

For PRs require work-ticket review before draft publication, exact-head target-applicable CI and promotion; no merge or cleanup                                 |

Reconcile receipt/checkpoint, register a new one-shot attention watch with gap reconciliation, then end the parent turn; child owns CI                                 |

Neither absence nor setup completion is a permission or handoff boundary |

A supplied “passing” fixture proves only the agent's decision under those observations. It does not prove checks ran or code changed. Report errors and revise guidance if a scenario exposes ambiguity; rerun only affected scenarios after repair.

Additionally exercise cycle-timeout renewal within the same absolute parent deadline/wake allowance; input attention followed by exact-job cancellation; fast completion during registration; unknown handoff without replay; and disconnect/reload coverage loss. Use stable settlement/input/shutdown filters across all replacements. A terminal job, outer attention handoff, child CI handoff, and semantic delivery are separate evidence.

## Controlled two-child exercise

Obtain explicit authority for two serial read-only Herdr worktrees/Pi sessions and ignored initial handoffs. Do not infer it from permission to implement one ticket. Require Background and permitted session-provider access already available; do not install, link, reload, create real tickets, or publish unrelated PRs for an exercise. Retain resources unless cleanup is separately authorized.

1. Commit the candidate skill in the owning implementation checkout so both children can read reachable source. Record the exact candidate head H. Inspect branches/paths and create child A through spin-out at H with a read-only verification brief, not a work-ticket implementation assignment. Do not let fixture identities become real Plane claims/checkpoints.
2. Start A, correlate its live session/incarnation, register a bounded one-shot Background session subscription before the task prompt, then submit the path-based handoff through Herdr without waiting. Ask A to assess the first four decision scenarios from supplied observations and report in its final response, without edits, commits, setup, or external calls. End the parent turn while pending.
3. On wake, reconcile receipt, full response, Git head and cleanliness, and observed quiescence. Accept the result only on evidence, not settlement. Keep the complete response in a parent-retained artifact; if terminal scrollback is insufficient, use Herdr's documented report-file fallback only with applicable artifact-write authority.
4. Only after accepting A, create B at A's verified commit H, targeting A's branch in its brief. Include A's exact branch/head and accepted result references. Ask B to assess the remaining scenarios, then repeat registration, submission, turn ending, and semantic reconciliation.
5. Retain both creation/start/prompt receipts, immutable identities, handoff paths, watch receipts/timestamps, clean statuses/heads, full responses, and the parent acceptance-before-successor-launch ordering. Record any missed event, unanswered question, failed decision, or unobserved boundary honestly.

This exercises real handoff transport, separate worktrees, one-shot observation, and observed serial reasoning. Read-only children have identical Git heads; they do **not** demonstrate changed stacked commits, child implementation/checkpoint writes, actual dependency installation, PR targeting, external CI, or promotion. Those remain model scenarios or separately observed delivery evidence. Do not label two read-only successes as two completed real tickets. A missing live seam is a concrete verification gap, not permission to simulate a successful receipt.
