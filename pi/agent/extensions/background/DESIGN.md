# Background design

Background separates execution lifetime from the foreground tool turn without replacing any executor. The adapter prepares its existing executor's authority and deadline; the service owns persisted admission, outcomes and attention. Admission first retires the oldest eligible terminal outcome when the rolling 256-completion window is full; unresolved attention and running work remain protected. A single validated atomic sidecar replacement includes retirement and admission so failed storage never launches work.

## Modules

- `api.ts`: supported host contract and session-bus discovery, independent of extension module-cache identity.
- `service.ts`: single-owner execution/attention lifecycle, copied receipts, finite admission, cancellation, dismissal and stale-completion suppression.
- `store.ts`: bounded validated session sidecar, exclusive owner-only staging, atomic rename and filesystem synchronization. Historical observer entries are never inspected.
- `index.ts`: Pi session/turn/context hooks, automatic readiness-based handoff and one persistently mounted below-editor widget.
- `config.ts`: validated presentation-only widget settings with global/project/environment precedence and config inspection.
- `visibility.ts`: pure handoff-age filtering, separate from service attention and retention predicates.

## Admission and storage

A stable UUID and immutable deadline are persisted before invoking adapter code. No work starts after failed admission. Each adapter is invoked once in a handled promise, and must use its original executor's deadline/abort implementation. Background never dispatches provider calls or schedules repeated work.

The session sidecar is separate from Pi's append-only custom entries: `appendEntry` can buffer writes before the first assistant message and does not provide a filesystem durability acknowledgment. A bounded atomic snapshot makes admission failure observable before execution and avoids unbounded receipt-update history. Store errors close admission and abort active work. Even a rename followed by failed directory synchronization is uncertain; no automatic resend or execution replay follows.

Records follow the rolling retention window: only terminal outcomes with observably consumed notifications or explicit dismissal are eligible for retirement at admission. Unresolved attention stays protected even after visual expiry. Branch visibility follows the admission anchor, while the sidecar retains all branches. Returning to an old branch surfaces interrupted outcomes. A fork does not inherit execution ownership or sidecar state. Persistence is cooperative single-owner storage, not a hostile same-user isolation mechanism.

## Attention and races

Terminal outcome and notification intent commit together. Before `sendMessage`, handoff becomes durably unknown. Only successful return marks handed-to-Pi and persists `notification.handedAt`; a throw retains uncertainty and no confirmed timestamp. This optional timestamp preserves historical sidecar compatibility without inventing old delivery times. Consumption remains a separate observation requiring context inclusion and a successful provider-response hook, not a send return, agent settlement, inspection, or task acceptance. Providers without that hook retain attention until dismissal. Trusted context/payload-transforming extensions limit what this observation proves.

The delivery pump checks queued messages, readable empty TUI draft and dialog depth, independently of runtime idleness, using the shared pure notification safety guard. Eligible messages steer active runs at Pi's supported boundary or start an ordinary idle run; current model/tool work is not aborted. It never mutates the editor. Readiness is checked again after persistence/observational callbacks and immediately before the Pi effect. A newly introduced safety hold restores the known-unattempted intent; failed rollback persistence remains conservative uncertainty. A one-second unref'ed timer catches hold clearance while busy without model polling or blocking lifecycle handlers. Timers are cleared on close. Each terminal run has at most one actual notification attempt; dismissed intent is suppressed, and already handed messages cannot be recalled.

Shutdown/reload and successful navigation revoke the service before aborting, persist conservative interrupted/unknown-effect state, and suppress late executor results. Restoration cannot recreate callbacks or renew deadlines. Canceled navigation leaves execution untouched. Storage failure retains in-memory uncertainty and forbids new work/notifications. Arbitrary synchronous trusted callbacks remain capable of blocking Pi; the service is not a sandbox.

## Widget visibility

A session-initialization snapshot controls automatic hiding: enabled by default, with one 15-second delay for all terminal states. The display-only predicate combines existing attention visibility with confirmed `notification.handedAt`; running records, pending/unknown handoffs and historical receipts without known handoff timing never expire. A local notification-ID set also pins live queued rows past that deadline. IDs enter before the synchronous Pi call so reentrant admission is observed; throws remove the known-queued projection and retain existing uncertainty. Matching custom `message_start` clears the queue indicator and refreshes the widget, without consumption writes or events. Dismissed/consumed/retired records prune the display set; lifecycle close clears it. Restoration never reconstructs queue membership. Admission restores the original handoff-age expiry policy, not a new clock. Execution elapsed remains based on `endedAt`, independently of the visibility clock. Navigation/restoration does not restart the delay. A generation guard prevents asynchronous configuration loading from restoring a closed or superseded service.

The existing one-second delivery-readiness timer also refreshes widget expiry, including with only terminal records. It remains unref'ed and is cleared on close. The last expired row removes the widget; repainting live rows retains their mounted component and sibling ordering. No separate timers, summaries, model turns, dismissal calls, consumption changes, persistence writes or lifecycle events are introduced by visual expiry. `service.ts` attention/capacity/retirement decisions must never use the presentation predicate. After confirmed handoff, execution warnings obey the configured expiry and remain in inspection/notifications. Muted pending/held delivery suffixes use readiness sampled at rendering, never a persisted hold or new attention state; dialog takes precedence over queued input and draft; unreadable inspection holds conservatively. Active agent work alone is not a hold. The config command rereads configured values without changing the session snapshot.

## Rendering and tests

`index.ts` registers Pi's custom renderer for `background:execution-outcome-v1`. Handoff adds only a versioned display snapshot (name, adapter, outcome and effect flags) alongside unchanged execution/notification correlation IDs. The loader-inert `_shared/notification.ts` projects one source/state-first content row with theme-provided notification background and safe expanded text. Optional batch cardinality controls singular wording without changing execution accounting. It receives no service handle or lifecycle callbacks. Missing/invalid metadata falls back without outcome inference. The complete original message and inspection reference remain model-facing; rendering/expansion cannot acknowledge consumption, persist, dismiss or replay. The existing context/provider-response hooks alone own consumption observation.

Widget rows lead with adapter source, semantic-colored lifecycle word and sanitized label, then nonzero disjoint child counts, reported tokens, elapsed time and actionable warnings. Unknown-effect/persistence/handoff warnings reserve space before optional identity and telemetry under width pressure. Dispatch/restoration flags do not prove writes, so generic effects-may-persist boilerplate is omitted for all projections. Actual outcome uncertainty remains visible as outcome unknown; conservative receipt metadata and no-replay behavior are unchanged. `display.ts` owns the execution vocabulary, counts, tokens and warning projection shared by widgets and tool summaries. Optional canceled counts are a subset of the historical unsuccessful aggregate, preserving persisted compatibility while separating failure from cancellation in new displays. IDs remain in inspection; combined critical warnings compact before optional names or telemetry. Child-count fields stay muted; semantic color belongs to primary state and actionable warnings. Ordinary primary queued/pending states use normal text, and timeout/cancellation/interruption use warning styling consistently across widgets, tool results and wakes. Delivery suffixes remain muted and never recolor the outcome; compact diagnostic explanations, IDs and no-replay guidance are muted, while expanded body/value text remains normal. Activity ellipses are omitted, while truncation ellipses remain. Adapters yield one event-loop turn after durable admission, then inspect the current receipt rather than returning a stale admission copy. This is a bounded snapshot, not completion polling: actual started/queued/fast-terminal state survives, and executor deadlines never renew. Subagent gate acquisition publishes departure from its queue before entering its existing executor. `render.ts` provides display-only shared adapter control summaries, including lowercase run state and short ID without duplicate name and available success telemetry from retained records with no live clock or artifact fetch. Tool results use the shared additive/wrapping component under the canonical [result convention](../_shared/README.md#tool-result-conventions); widgets/wakes retain their separate layouts. Historical foreground Subagent/Workflow results use sanitized text rather than legacy progress layouts. Optional progress snapshots validate monotonic counts and bounded partial outcomes before atomic persistence. Dynamic workflow activity separately records started/settled logical calls and a sanitized phase; it never relaxes fixed batch totals. A single subagent reports bounded profile and phase/tool-name activity through the same validated receipt, without tool arguments; its widget omits 0/1 settled. Profile/phase remain inspectable but are omitted from the compact widget. Single-child widgets show reported tokens instead of redundant counts. All execution widgets, including Script, use the persisted admission clock for truthful elapsed time, repainting during running work on the existing one-second readiness timer without writes or renewed deadlines. Initial result references can be persisted with admission so interruption before adapter startup does not lose the prepared inspection path. They produce no telemetry event or notification; interruption preserves the last snapshot. Existing Script adapters need not report progress. Shared fitting truncates each row to terminal width without wrapping. The shared persistent-widget helper repaints instead of reinserting keys; no animation, fabricated percentages or sibling reordering is introduced.

Tests cover durable-before-run ordering, cancellation, capacity, storage faults, no-replay uncertainty, restoration and stale callbacks, real Script subprocess outcomes/revocation, actual event-bus listener payloads, tool controls, draft deferral and narrow/hostile rendering. Interactive qualification remains a separate delivery requirement; unit fixtures alone do not prove a live conversation remains responsive.
